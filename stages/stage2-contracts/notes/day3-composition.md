# Day 3 학습 노트 — 상속 vs 조합: has-a로 기능을 조립하기

> 이론 30분용 노트. 다 읽고 나서 `exercises/day3-composition.ts`를 연다.
> 예시 도메인은 실습(알림+로거)과 다르게 **차량·엔진, 플레이어·저장소** 등으로 잡았다.

---

## 오늘의 학습 목표

1. **is-a(상속)** 와 **has-a(조합)** 를 문장으로 구분하고 코드로 판별한다.
2. 상속이 만드는 **강한 결합**과 **fragile base class 문제**를 이해한다.
3. "왜 상속보다 조합인가"를 교체 가능성·테스트 용이성으로 설명한다.
4. 계약(interface)을 **생성자로 주입**받는 조합 코드를 직접 그린다.
5. 이 조합이 다음 단계의 **DI(의존성 주입)** 로 어떻게 이어지는지 감을 잡는다.

---

## 개념 설명

### 1. 상속은 "A는 B다(is-a)"

상속(`extends`)은 강한 관계다. `Dog extends Animal`은 "개는 동물**이다**"라는 선언이고, 이건 참이다. 그래서 상속 자체가 나쁜 건 아니다. 문제는 **"is-a"가 아닌데 코드 재사용을 위해 상속을 남용**할 때 생긴다.

```ts
// 나쁜 신호: "기능을 얻으려고" 상속한다
class Logger {
  log(msg: string) { console.log(msg); }
}
// "차량이 로거의 일종"이라고? 말이 안 된다.
class Car extends Logger {
  drive() { this.log('출발'); }
}
```

`Car`는 `Logger`가 **아니다**. 로그를 "쓰고 싶었을" 뿐인데 상속으로 붙였다. 여기서 문제가 시작된다.

### 2. 상속의 세 가지 대가

**(a) 강한 결합.** 자식은 부모의 public/protected 전부를 물려받는다. `Car`가 `log()` 말고도 `Logger`의 모든 내부 사정에 묶인다. 부모가 바뀌면 자식이 흔들린다.

**(b) 교체가 어렵다.** 로그를 콘솔 → 파일 → 원격 서버로 바꾸려면, `Car`가 상속한 부모 클래스 자체를 갈아야 한다. 로깅 방식을 런타임에 바꾸는 건 불가능하다.

**(c) 다중 상속 불가.** TS/JS는 한 클래스가 하나만 `extends`한다. `Car`가 로깅도 하고 계측(metrics)도 하려면? 상속으론 둘 다 못 붙인다.

### 3. fragile base class 문제 (깨지기 쉬운 부모 클래스)

상속의 가장 음험한 함정이다. **부모 클래스를 "안전하게" 수정했는데 자식이 깨지는** 현상이다.

```ts
class Base {
  save(x: number) { this.write(x); }
  write(x: number) { /* ... */ }
}
class Child extends Base {
  private count = 0;
  // save를 오버라이드해서 카운트를 세려고 했다
  save(x: number) { this.count++; super.save(x); }
}
```

여기서 부모가 나중에 "최적화"라며 `save`가 내부에서 `write`를 두 번 부르도록 바꾸면? 자식의 `count`는 실제 저장 횟수와 어긋난다. **부모의 내부 구현 변경이 자식의 정확성을 깬다.** 자식은 부모의 "공개 계약"이 아니라 "내부 호출 순서"에 몰래 의존하고 있었던 것이다. 이게 fragile base class다 — 상속은 캡슐화를 약하게 뚫는다.

### 4. 조합은 "A는 B를 가진다(has-a)"

조합(composition)은 필요한 기능을 **필드로 가지고(has-a)** 위임한다.

```ts
interface Logger {
  log(message: string): void;
}

class Car {
  // "Car는 Logger를 가진다" — 주입받아 보관
  constructor(private readonly logger: Logger) {}
  drive() {
    this.logger.log('출발'); // 위임
  }
}
```

`Car`는 이제 `Logger`가 **아니고**, `Logger`를 **가진다**. 그리고 결정적으로, 받는 타입이 **구체 클래스가 아니라 `Logger` 인터페이스**다. 그래서:

```ts
class ConsoleLogger implements Logger { log(m: string) { console.log(m); } }
class SilentLogger  implements Logger { log(_: string) {} }

new Car(new ConsoleLogger()); // 콘솔로
new Car(new SilentLogger());  // 조용히
// 테스트에선 가짜 로거를 꽂아 "무엇이 로깅됐는지" 검증
```

**교체 가능**하고(런타임에 다른 구현 주입), **테스트 가능**하다(스파이 로거로 호출 내용 확인). fragile base class도 없다 — `Car`는 `Logger`의 **공개 계약(`log`)** 에만 의존하지 내부 구현엔 손대지 않는다.

### 5. 판별 규칙

> **"A는 B다"가 자연스러우면 상속, "A는 B를 가진다/쓴다"가 자연스러우면 조합.**

- "개는 동물이다" → 상속 OK
- "차는 엔진**을 가진다**", "플레이어는 저장소**를 쓴다**", "서비스는 로거**를 가진다**" → 조합
- 애매하면 조합을 택하라. 조합은 되돌리기 쉽고, 상속은 한 번 묶이면 풀기 어렵다. **"상속보다 조합을 선호하라(Favor composition over inheritance)"** 는 그래서 나온 격언이다.

### 6. 조합의 또 다른 이점 — 기능을 "여러 개" 붙일 수 있다

상속은 하나만 `extends` 할 수 있어 기능을 하나밖에 못 물려받는다. 조합은 필요한 만큼 **여러 협력자를 주입**할 수 있다.

```ts
interface Logger  { log(m: string): void; }
interface Metrics { count(name: string): void; }

class Car {
  constructor(
    private readonly logger: Logger,   // 로깅 기능
    private readonly metrics: Metrics, // 계측 기능 — 둘 다 붙였다
  ) {}
  drive() {
    this.logger.log('출발');
    this.metrics.count('drive');
  }
}
```

상속으로는 `Logger`와 `Metrics`를 동시에 못 붙인다(다중 상속 불가). 조합은 생성자에 인자를 하나 더 늘리면 끝이다. **기능을 레고처럼 조립**하는 이 유연함이 조합을 실무 기본값으로 만든 결정적 이유다.

> 정리: 조합은 (1) 교체 가능, (2) 테스트 가능, (3) fragile base class 없음, (4) 기능을 여러 개 조립 가능 — 네 가지를 모두 얻는다.

## 실무·채용 연결

- 실무 코드의 서비스 클래스는 거의 다 조합이다. `constructor`가 여러 계약을 받아 필드로 보관하는 형태 — 이게 **의존성 주입(DI)** 의 골격이다.
- **NestJS의 `constructor(private readonly userService: UserService)`** 가 정확히 이 조합이다. 서비스가 다른 협력자를 "상속"하는 게 아니라 "주입받아 가진다".
- "상속과 조합의 차이를 설명하라", "왜 조합을 선호하나"는 면접 단골이다. **fragile base class**나 **다중 상속 불가**를 근거로 대면 깊이가 드러난다.
- 테스트를 우대하는 조직(국내 테크 기업 등)에서 조합은 필수다. 협력자를 주입받으면 테스트에서 가짜를 꽂을 수 있어, **단위 테스트가 쉬워진다**. 상속으로 묶인 코드는 부모까지 통째로 끌고 와야 해서 테스트가 무겁다.

## 흔한 실수와 함정

1. **재사용을 위해 상속** — "저 클래스에 쓸 만한 메서드가 있으니 상속하자"는 대부분 신호가 잘못됐다. 그건 has-a다. 주입받아라.
2. **주입 타입을 구체 클래스로 지정** — `constructor(logger: ConsoleLogger)`로 받으면 교체 가능성이 죽는다. **인터페이스(계약) 타입**으로 받아야 한다. 이게 조합의 핵심이자 다음 날 배울 DIP의 씨앗이다.
3. **내부 배열/객체를 그대로 반환** — 테스트용으로 모아둔 컬렉션을 `return this.items`로 넘기면 외부에서 원본을 수정할 수 있다(캡슐화 깨짐). `[...this.items]`처럼 **복사본**을 반환하라.
4. **주입은 해놓고 위임하지 않음** — 필드로 받아만 두고 실제 로직에서 `this.logger.log(...)`를 안 부르면 조합의 의미가 없다. 받은 협력자를 실제로 써야 한다.

## 오늘 실습과의 연결

`exercises/day3-composition.ts`는 "로거를 상속하지 말고 주입받으라"는 문제다.

- 알림을 보내는 서비스가 로깅 기능을 **상속이 아니라 조합**으로 얻는다. 위의 `Car`가 `Logger`를 주입받은 구도 그대로다.
- 주입 타입은 반드시 **인터페이스**로 받아라. 구체 로거 클래스로 받으면 문제의 핵심을 놓친 것이다(함정 2번).
- 테스트용 인메모리 로거는 쌓인 로그를 반환할 때 **복사본**을 넘겨야 한다(함정 3번).
- 서비스의 동작은 "로깅 → 조건 검사 → (실패 시) 로깅 후 종료 / (성공 시) 로깅 후 성공" 같은 **호출 순서**가 정해져 있다. 주석의 1→2→3 순서를 그대로 옮기고, 각 분기에서 어떤 메시지를 남기는지 문자열까지 맞춰라.
