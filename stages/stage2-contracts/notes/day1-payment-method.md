# Day 1 학습 노트 — interface와 implements: 계약으로서의 인터페이스

> 이론 30분용 노트. 다 읽고 나서 `exercises/day1-payment-method.ts`를 연다.
> 여기 나오는 코드 예시는 **실습과 다른 도메인**(도형·동물 등)이다. 답을 훔쳐보는 게 아니라 원리를 손에 붙이는 게 목적.

---

## 오늘의 학습 목표

1. 인터페이스가 "구현"이 아니라 "**계약(약속된 모양)**"이라는 것을 설명할 수 있다.
2. `implements`가 TypeScript의 **구조적 타이핑**에서 실제로 무엇을 강제하는지 안다.
3. 하나의 계약을 여러 클래스가 다르게 구현할 때 생기는 **다형성**을 코드로 그린다.
4. "사용하는 쪽이 구체 클래스를 모른다"는 문장의 의미를 함수 시그니처 단위로 이해한다.
5. `readonly`, 인터페이스 메서드 시그니처 등 계약을 적을 때의 문법 관례를 익힌다.

---

## 개념 설명

### 1. 인터페이스는 "무엇을(what)"만 말한다

인터페이스는 **모양의 명세**다. "이 타입이라면 이런 프로퍼티와 메서드가 반드시 있어야 한다"만 규정하고, 그 메서드가 **어떻게(how)** 동작하는지는 한 글자도 담지 않는다.

```ts
// 도형이라면 "넓이를 구할 수 있어야 한다"는 계약
interface Shape {
  readonly kind: string;
  area(): number;
}
```

`Shape`는 실행 가능한 코드가 아니다. 컴파일되면 사라진다(런타임에 존재하지 않는다). 오직 **컴파일 타임에 타입을 검사하는 자(尺)** 일 뿐이다.

### 2. `implements` — "이 계약을 지키겠다는 선언"

클래스가 `implements Shape`라고 쓰면, 컴파일러는 "너는 정말 `kind`와 `area()`를 가지고 있느냐"를 검사한다. 빠뜨리면 컴파일 에러다.

```ts
class Circle implements Shape {
  readonly kind = 'circle';
  constructor(private readonly radius: number) {}
  area(): number {
    return Math.PI * this.radius ** 2;
  }
}

class Rectangle implements Shape {
  readonly kind = 'rectangle';
  constructor(private readonly w: number, private readonly h: number) {}
  area(): number {
    return this.w * this.h;
  }
}
```

`Circle`과 `Rectangle`은 **완전히 다른 계산식**을 갖지만, 둘 다 "넓이를 구할 수 있다"는 `Shape` 계약을 만족한다. 계산 방식(how)이 다를 뿐 약속(what)은 같다.

### 3. 구조적 타이핑에서 `implements`의 진짜 의미

여기서 자바 경험자가 자주 놓치는 지점이다. TypeScript는 **구조적(structural) 타이핑**이다. "이름이 아니라 모양이 같으면 같은 타입으로 본다."

```ts
function printArea(s: Shape) {
  console.log(`${s.kind}: ${s.area()}`);
}

// implements를 안 붙였는데도 통과한다 — 모양이 Shape와 같으니까
const triangle = {
  kind: 'triangle',
  area() { return 6; },
};
printArea(triangle); // OK. 구조가 맞으면 받아준다
```

즉 `Shape`를 만족하는지는 `implements` 키워드가 결정하는 게 아니라 **실제 프로퍼티/메서드 구조**가 결정한다. 그렇다면 `implements`는 왜 쓰는가?

- `implements`는 **개발자에게 주는 컴파일 타임 안전벨트**다. "나는 이 계약을 지킬 의도다"라고 명시하면, 계약을 어겼을 때 그 클래스 정의 지점에서 바로 에러가 난다. 사용처까지 가서 터지지 않는다.
- 문서화 효과도 크다. 클래스 선언만 봐도 "이건 Shape 역할을 하는구나"가 읽힌다.

핵심 정리: **구조가 계약을 만족시키고, `implements`는 그 의도를 컴파일러에 등록해 조기 검출한다.**

### 4. 다형성 — 사용하는 쪽이 구체를 모른다

가장 중요한 부분이다. 계약에 의존하는 함수를 보자.

```ts
function totalArea(shapes: Shape[]): number {
  return shapes.reduce((sum, s) => sum + s.area(), 0);
}

const shapes: Shape[] = [
  new Circle(2),
  new Rectangle(3, 4),
  // 나중에 Triangle, Pentagon을 100개 추가해도...
];
totalArea(shapes); // ...이 함수는 한 줄도 안 바뀐다
```

`totalArea`는 원인지 사각형인지 **전혀 모른다**. 오직 `Shape`라는 추상만 안다. 그래서 도형 종류가 늘어나도 이 함수는 불변이다. 이것이 **다형성(polymorphism)** 이고, 다음 스테이지 내내 나올 OCP(개방-폐쇄 원칙)의 씨앗이다.

> 기억할 문장: **"변하는 것(구체 클래스)과 변하지 않는 것(계약에 의존하는 로직)을 가른다."**

### 5. 곁가지 — `interface` vs `type` 별칭

계약을 적을 때 `interface`뿐 아니라 `type`으로도 비슷하게 쓸 수 있어 헷갈린다.

```ts
interface Shape { area(): number; }        // 인터페이스
type ShapeT = { area(): number };          // 타입 별칭 — 거의 같은 역할
```

둘 다 클래스가 `implements` 할 수 있다. 실무 관례상:

- **객체/클래스의 계약**을 정의할 땐 `interface`를 기본으로 쓴다(확장·선언 병합에 유리하고, 에러 메시지가 읽기 좋다).
- **유니온·튜플·매핑 타입** 등 객체가 아닌 형태를 표현할 땐 `type`을 쓴다(예: `type Id = string | number`).

이번 스테이지에서 계약은 대부분 `interface`로 온다. "왜 type이 아니라 interface냐"를 물으면 위 기준으로 답하면 된다. 지금은 **"계약을 정의하는 두 문법이 있고, 클래스 계약엔 interface가 관례"** 정도만 챙기면 충분하다.

## 실무·채용 연결

- **채용 우대사항 단골인 "객체지향 설계에 대한 이해"**는 이 지점에서 시작한다. "인터페이스에 의존하는 코드를 짜봤는가"는 신입~주니어 면접 단골이다.
- 실무 코드에서 `Repository`, `Gateway`, `Provider` 같은 이름이 붙은 것들은 거의 다 인터페이스(계약)다. 서비스 로직은 그 계약에만 의존하고, 실제 DB/외부 API 구현은 나중에 갈아끼운다.
- **NestJS**의 컨트롤러가 서비스를 받을 때, 우리는 대개 구체 클래스가 아니라 "그 역할"에 의존하도록 설계한다. Day5에서 이 구조의 축소판을 직접 만든다.
- 테스트 관점: 계약에 의존하면 **가짜(fake/mock) 구현**을 꽂아 테스트할 수 있다. `Shape`를 받는 함수는 `{ kind:'x', area:()=>10 }` 같은 즉석 객체로도 검증된다. TDD를 우대하는 조직이 이 설계를 선호하는 이유다.

## 흔한 실수와 함정

1. **`implements`를 붙이면 구현이 채워진다고 오해** — 아니다. 인터페이스는 구현을 하나도 주지 않는다. 메서드 본문은 클래스가 전부 직접 써야 한다. (부분 구현을 물려주는 건 Day2의 추상 클래스다.)
2. **`readonly` 프로퍼티를 생성자 밖에서 바꾸려 함** — 계약이 `readonly name`이라면 초기화 이후 재할당이 막힌다. 초기값이나 생성자에서만 정한다.
3. **반환 타입을 계약과 미묘하게 다르게 씀** — 계약이 `{ success: boolean; receipt: string }`을 요구하는데 한 필드를 빠뜨리거나 이름을 틀리면, 사용처가 아니라 그 클래스에서 에러가 난다(이게 `implements`의 이점이다).
4. **사용하는 쪽에서 구체 타입으로 좁혀버림** — `function f(m: CreditCardPayment)`처럼 구체 클래스로 받으면 다형성이 죽는다. 항상 **가장 추상적인 계약 타입**으로 받아라.

## 오늘 실습과의 연결

`exercises/day1-payment-method.ts`에는 `PaymentMethod`라는 계약이 **이미** 정의돼 있다. 너의 일은 이 하나의 계약을 세 클래스로 **다르게 구현**하는 것이다.

- 세 구현은 `name` 값과 영수증 접두사만 다르고, "금액 검증"이라는 뼈대는 닮아 있다. 위 `Circle`/`Rectangle`이 계산식만 다르고 계약은 같았던 것과 같은 구도다.
- 그중 하나는 **상태(잔액)를 가진다.** 결제가 성공하면 상태가 줄고, 실패하면 그대로여야 한다 — 실패 경로에서 상태를 건드리지 않는 순서 감각을 여기서 잡아라.
- 파일 맨 아래 사용처 함수는 **이미 완성**돼 있고 구체 클래스를 모른다. 그 함수를 다시 짜려 하지 말고, "이게 다형성이구나"를 눈으로 확인만 해라.
- 힌트는 각 메서드 위 주석에 한국어로 붙어 있다. 검증 실패 메시지 문자열은 **토씨 하나까지** 주석 그대로 맞춰야 테스트가 통과한다.
