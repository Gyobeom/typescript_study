## 개념 설명

### 1. 인터페이스의 한계 → 추상 클래스의 등장

Day1의 인터페이스는 구현을 하나도 못 담았다. 그래서 여러 구현이 **같은 코드를 반복**하면 인터페이스로는 그 중복을 없앨 수 없다.

```ts
// 인터페이스만 쓰면: 공통 흐름을 각 클래스가 매번 다시 적어야 한다
interface Beverage {
  make(): string;
}
class Coffee implements Beverage {
  make() { return ['물 끓이기', '커피 내리기', '컵에 붓기'].join(' → '); }
}
class Tea implements Beverage {
  make() { return ['물 끓이기', '찻잎 우리기', '컵에 붓기'].join(' → '); }
}
```

"물 끓이기"와 "컵에 붓기"는 똑같은데 두 번 적혔다. 음료가 늘수록 이 중복도 늘어난다. **공통 흐름을 한 곳에 두고 싶다** — 이게 추상 클래스가 필요한 이유다.

### 2. 추상 클래스 = 계약 + 부분 구현

추상 클래스는 **일부는 구현해 두고, 달라지는 부분만 `abstract`로 비워** 하위 클래스에 위임할 수 있다.

```ts
abstract class Beverage {
  // 템플릿 메서드: 전체 흐름(순서)은 여기서 고정된다
  make(): string {
    return [this.boilWater(), this.brew(), this.pour()].join(' → ');
  }

  // 공통 단계는 부모가 구현해 준다 (부분 구현)
  protected boilWater(): string { return '물 끓이기'; }
  protected pour(): string { return '컵에 붓기'; }

  // 음료마다 다른 단계만 계약(빈칸)으로 남긴다
  protected abstract brew(): string;
}

class Coffee extends Beverage {
  protected brew(): string { return '커피 내리기'; }
}
class Tea extends Beverage {
  protected brew(): string { return '찻잎 우리기'; }
}
```

이제 `Coffee`와 `Tea`는 **자기만의 차이(`brew`) 한 조각만** 채우면 된다. 공통 흐름과 공통 단계는 부모에서 한 번만 작성된다. 중복이 사라졌다.

### 3. 템플릿 메서드 패턴 — 흐름은 고정, 세부는 위임

위의 `make()`가 **템플릿 메서드**다. 특징:

- **호출 순서를 부모가 결정한다.** `boilWater → brew → pour`. 하위 클래스가 순서를 못 바꾼다.
- **달라지는 지점만 `abstract`로 뚫어 둔다.** 하위 클래스는 그 구멍만 메운다.
- 결과적으로 "전체 알고리즘의 골격은 유지하면서, 특정 단계만 서브클래스가 재정의"하게 된다.

```
make() ─┬─ boilWater()  (부모 구현, 공통)
        ├─ brew()       (abstract → 자식이 채움)  ← 여기만 갈라진다
        └─ pour()       (부모 구현, 공통)
```

이 구조는 실무의 "파이프라인이 정해져 있고 한두 단계만 커스터마이즈"하는 상황에 잘 맞는다. 예: 요청 처리 흐름(인증 → 검증 → 처리 → 응답)에서 "처리" 단계만 라우트마다 다르게.

### 4. `protected`가 여기 쓰이는 이유

- `public`: 외부(사용처)도 부른다. 위 예의 `make()`가 그렇다.
- `protected`: **자신과 하위 클래스만** 부른다. `brew`, `boilWater`는 `make` 내부에서만 쓰이는 조립 부품이므로 외부에 노출할 필요가 없다.
- `private`: 자기 클래스만. 하위 클래스도 못 본다 → 오버라이드할 조각에는 못 쓴다.

그래서 "하위 클래스가 채우거나 재사용할 조각"은 대개 `protected`다.

### 5. 추상 클래스 vs 인터페이스 — 선택 기준

| 질문 | 인터페이스 | 추상 클래스 |
|---|---|---|
| 구현(코드)을 물려줄 게 있나? | ❌ 없다 | ✅ 있다 (공통 흐름/필드) |
| 한 클래스가 여러 개 채택 가능? | ✅ 여러 개 `implements` | ⚠️ 하나만 `extends` (단일 상속) |
| "역할/능력"만 규정? | ✅ 딱 맞음 | 과함 |
| "골격 + 빈칸" 구조? | 부족 | ✅ 템플릿 메서드에 최적 |

경험칙:

- **공유할 구현이 없고 "능력"만 규정** → 인터페이스. (`Comparable`, `Serializable` 같은 것)
- **여러 구현이 공통 흐름/상태를 나눠 갖고, 일부만 다름** → 추상 클래스.
- 헷갈리면 **인터페이스를 기본값**으로 두고, 중복 구현이 실제로 쌓일 때만 추상 클래스로 올려라. 인터페이스가 더 유연하다(단일 상속 제약이 없다).

## 실무·채용 연결

- "인터페이스와 추상 클래스의 차이를 설명하라"는 **면접 최빈출** 질문이다. 표로 외우지 말고 "구현을 담느냐"와 "단일 상속 제약"이라는 두 축으로 설명하면 확실히 우위다.
- 프레임워크의 `AbstractController`, `BaseRepository` 류가 템플릿 메서드로 짜인 경우가 많다. 공통 CRUD 흐름은 베이스가 갖고, 엔티티별 차이만 오버라이드한다.
- 다만 실무 트렌드는 **상속(추상 클래스)보다 조합**으로 기운다(Day3에서 다룸). 추상 클래스는 강력하지만 상속의 결합 비용을 함께 진다. "언제 추상 클래스가 과한가"를 아는 게 Day3~4로 가는 다리다.

## 흔한 실수와 함정

1. **템플릿 메서드를 하위 클래스에서 오버라이드해버림** — 흐름 고정이 깨진다. 부모의 `make()`(전체 흐름)는 건드리지 말고, 비워둔 `abstract` 조각만 채워라.
2. **`abstract` 메서드에 본문을 씀** — `abstract`는 시그니처만 있고 본문이 없어야 한다. 본문이 필요하면 그건 일반 메서드다.
3. **부모가 제공하는 공통 헬퍼를 무시하고 자식에서 다시 계산** — 예를 들어 부모가 합계 계산 헬퍼를 protected로 주면, 자식은 그걸 **호출**해서 재사용해라. 직접 다시 합산하면 중복이다.
4. **`private`로 뚫어놓고 자식에서 못 채워 당황** — 오버라이드 대상은 `protected abstract`여야 한다.

## 오늘 실습과의 연결

`exercises/day2-report-generator.ts`의 추상 클래스는 **전체 흐름(템플릿 메서드)과 공통 헬퍼가 이미 완성**돼 있다. 너는 이걸 상속한 **두 하위 클래스**를 만든다.

- 두 하위 클래스는 **같은 골격**을 공유하되, 각자 다른 출력 형식을 낸다. 위 예의 `Coffee`/`Tea`가 `brew`만 달랐던 것과 정확히 같은 구도다.
- 부모가 protected로 제공하는 **공통 계산 헬퍼**가 있다. 자식의 마지막 조각에서 그걸 **재사용**하라 — 직접 다시 계산하지 말 것(위 함정 3번).
- 각 조각이 반환할 문자열 형식은 주석의 예시 출력에 **정확히** 나와 있다. 개행(`\n`)과 구분자, 접두사를 토씨까지 맞춰라.
- 전체 흐름 메서드는 오버라이드하지 마라. 너의 손이 닿을 곳은 `abstract`로 비워진 조각들뿐이다.
